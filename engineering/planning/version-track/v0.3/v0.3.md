# v0.3 — Operations and secrets console

*Last updated: 2026-09-26*

**Status:** 🚧 In Progress · **Type:** Feature · **Started:** 2026-09-24 · **Completed:** —

### Iteration 1 — Deployment operations

- [x] Ability to see why a deployment was refused or failed, without exposing setting values.
- [x] Ability to print a service's settings skeleton from its release contract.
- [x] Fix health probes failing when a service restricts its allowed hosts.
- [x] Ability to see recent deployments with outcome, reason, actor and release after a reload.
- [x] Ability to check a target's readiness without changing it.
- [x] Ability to see the release each target runs and whether it is locked.
- [x] Ability to reconcile an interrupted or failed deployment from the dashboard.
- [x] Ability to rehearse deployments against a local SSH target.

### Iteration 2 — Dashboard

- [x] Ability to move between overview, deployments, fleet, secrets and products pages.
- [x] Ability to redeploy an earlier release from the deployment history.
- [x] Ability to collapse the sidebar to an icon rail with Ctrl/⌘ B or its edge handle, remembered per browser.
- [x] Ability to reach sign-out and the API status from the profile menu at the sidebar's foot.
- [x] Ability to switch between light, dark and system themes from the profile menu, remembered per browser.
- [x] Ability to deploy from a page header or a history row through one dialog: choose, confirm, follow.
- [x] Ability to see each deployment figure's change against the previous 30 days.
- [x] Ability to scan long lists with a pinned header, hover rows and status dots.
- [x] Ability to see placeholders shaped like each panel while its first load runs.

### Iteration 3 — Secrets console

- [x] Ability to see each configured vault and whether it is sealed.
- [x] Ability to browse namespaces and secret metadata without revealing values.
- [x] Ability to create a namespace and to set or rotate a secret value.
- [x] Ability to disable and re-enable a secret.
- [x] Ability to mint a product token shown once, and to revoke tokens.

### Iteration 4 — Metrics dashboard

- [x] Ability to see each server's load, memory, disk and uptime without changing it.
- [x] Ability to see each target's containers with state, health, restarts, CPU and memory.
- [x] Ability to see 30-day deployment metrics: deploys per day, success rate, rollout time and recovery time.
- [x] Ability to see which targets run an older release than the latest published one.
- [x] Ability to see secrets and product tokens due for rotation.
- [x] Ability to see everything that needs attention on the overview.
- [x] Ability to tell a manual vitals refresh ran: values turn into placeholders and back, even when unchanged.

### Iteration 5 — Local environment

- [x] Ability to run Wheelhouse in its production image against the local target and vault with one command.
- [x] Ability to deploy from the containerized console over SSH, as on a VPS.
- [x] Ability to run Wheelhouse from an IDE against the local rig, marked by a `Local rig` badge.
- [ ] Ability to sign in to the local console through a localhost GitHub OAuth app.

### Iteration 6 — Verification

- [ ] Deploy a release to the local target → history shows the outcome after a reload.
- [ ] Blank a required setting → the check names the key; a deploy changes nothing.
- [ ] Interrupt a rollout → reconciling from the dashboard unlocks the target.
- [ ] Set a secret in the console → a product token reads the new version.
- [ ] Stop a container on the local target → the fleet page shows it stopped and the overview flags it.
- [ ] Deploy a broken release → the overview's failure count and success rate change.
- [ ] Open the secrets page → each secret and token shows its age; overdue ones are flagged.
- [ ] Run `rehearse.py console`, sign in with GitHub and open every page → each page loads without errors.
